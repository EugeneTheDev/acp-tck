## Explanation of every non-PASS

### ACP-INIT-003 (MANDATORY) — FAIL for both, expected

Both agents echo the client's unsupported requested version (`65535`) verbatim in
`initialize`'s `protocolVersion` field instead of returning their own latest supported
version. This is the deliberately **strengthened** assertion from
`.agents/research/testy-cross-check.md` finding 1 / `.agents/plan.md` "ACP-INIT-003
strengthening": the previous, weaker test (success + integer type only) was a false negative
against exactly this defect, which both independent SDKs exhibit. Expected, not a TCK bug —
this FAIL is the correct outcome and is why the `--cancel-prompt`-driven cross-check is not
overall CONFORMANT for either fixture; see `tests/fixtures/agents/echoes_any_version.py` for the
in-repo self-test of the same defect.

Transcript (testy):

```
--> {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":65535,"clientCapabilities":{}}}
<-- {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":65535, ...}}
```

### ACP-INIT-004 (ADVISORY) — FAIL for both, expected

Neither agent ever sets `agentInfo` in the `initialize` result. Confirmed upstream: `testy`
never sets it anywhere in the Rust SDK (`testy-cross-check.md` §2.2), and `echo_agent.py`
returns a bare `InitializeResponse(protocol_version=protocol_version)` with no `agent_info`.
Expected per the research's predicted scorecard.

### ACP-JSONRPC-004 (ADVISORY) — FAIL for echo_agent only, genuine agent behaviour (new since the research)

Not predicted by `testy-cross-check.md` (which measured `echo_agent` returning `-32601` for an
unknown method via the router). Investigated: this is real, current SDK behaviour, not a TCK
bug. `EchoAgent` in `examples/echo_agent.py` subclasses `acp.Agent` directly rather than merely
satisfying it structurally. `acp.interfaces.Agent` (a `Protocol`) declares a default,
no-op `async def ext_method(self, method, params) -> ...` body; because `EchoAgent` inherits
from the class rather than just implementing the protocol, it inherits that stub, which
implicitly returns `None`. `acp/agent/router.py`'s `_handle_extension_request` calls
`getattr(agent, "ext_method", None)` — this now finds the inherited stub (not `None`), calls it,
and forwards whatever it returns as the JSON-RPC `result`, instead of raising
`RequestError.method_not_found`.

Measured transcript:

```
--> {"jsonrpc":"2.0","id":2,"method":"_tck/does_not_exist"}
<-- {"jsonrpc":"2.0","id":2,"result":null}
```

Since ACP-JSONRPC-004 only concerns the ADVISORY "SHOULD respond -32601" wording (the MANDATORY
"must respond at all" is ACP-EXT-001, which still PASSes — a `result: null` is still *a*
response), this does not affect the overall verdict and requires no TCK change: weakening the
assertion to accommodate a no-op default extension handler would defeat the purpose of the
check. Left as documented, genuine SDK behaviour.

### CAPABILITY-tier SKIPPED for echo_agent — expected

`echo_agent.py`'s `InitializeResponse` never sets `agentCapabilities` at all, so every
capability-conditional (CAPABILITY-tier) test correctly SKIPs as "not advertised" rather than
FAILing — this is exactly the four-status verdict model's intended behaviour for an agent that
implements only the baseline surface, and matches the research's note that `echo_agent` cannot
be used for any capability-conditional cross-check.

### ACP-CANCEL-001/002 (MANDATORY) — SKIPPED for echo_agent, expected

`echo_agent.py` has no cancellation handling at all and resolves every prompt in single-digit
milliseconds, so `session/cancel` can never be sent before the response arrives. Matches the
research's prediction ("permanently SKIPPED", `testy-cross-check.md` §3.2, Testability note 3).

### ACP-AUTH-004 (CAPABILITY) / ACP-AUTH-005 (ADVISORY) — differ by design, not a deviation

`testy` advertises `authMethods` and `auth.logout`, so AUTH-004 (logout, gated on the capability
marker) runs and PASSes, while AUTH-005 (the empty-`authMethods` negative control) correctly
SKIPs. `echo_agent` advertises neither, so AUTH-004 SKIPs (capability not advertised) and
AUTH-005 (the negative control for the no-`authMethods` case) applies and PASSes. Both are the
capability-gating machinery working as designed, not a TCK bug or an unexpected agent behaviour.

## Conclusion

No TCK bug was found: `testy`'s scorecard matches the predicted scorecard in
`.agents/research/testy-cross-check.md` §3.1 exactly (once accounting for the already-decided
ACP-INIT-003 strengthening). `echo_agent`'s scorecard matches the prediction except for one new,
genuine ADVISORY-tier finding (ACP-JSONRPC-004, explained above) that reflects real upstream SDK
behaviour introduced after the research was written, not a TCK defect. No assertion was weakened
to accommodate either agent.
